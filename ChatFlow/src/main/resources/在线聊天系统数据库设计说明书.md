# 在线聊天系统数据库设计说明书

版本：V1.0　｜　日期：2026-10-21　｜　配套文档：《在线聊天系统概要设计说明书》

## 1 设计规范

### 1.1 总体约定

| 项目 | 约定 |
| --- | --- |
| 数据库 | MySQL 8.0.x，库名 minichat |
| 引擎 | InnoDB（支持事务、行锁） |
| 字符集 | utf8mb4，排序规则 utf8mb4\_0900\_ai\_ci（支持 emoji） |
| 时区 | 数据库与应用统一 Asia/Shanghai（+08:00），时间字段使用 DATETIME |
| 外键 | 不建物理外键，应用层保证一致；关联列一律建索引 |
| 表前缀 | t\_，小写下划线命名；字段小写下划线；索引 idx\_ / uk\_ / ft\_ 前缀 |
| 注释 | 所有表与字段必须带 COMMENT |

### 1.2 类型规范

| 用途 | 类型 | 说明 |
| --- | --- | --- |
| 主键 | BIGINT | 业务表自增；t\_message 使用雪花 ID（应用生成） |
| 枚举、状态 | TINYINT | 含义见第 4 章枚举字典，代码中对应枚举类 |
| 布尔 | TINYINT(1) | 0 否，1 是 |
| 短文本 | VARCHAR(n) | 按实际长度设定，避免过大 |
| 长文本 | TEXT / MEDIUMTEXT | 消息正文用 TEXT，AI 回复用 MEDIUMTEXT |
| 扩展数据 | JSON | 仅存放不参与过滤的附加信息 |
| 金额或计数 | INT / BIGINT | 本系统无金额；token 与未读使用 INT / BIGINT |
| 时间 | DATETIME / DATETIME(3) | 消息创建时间使用毫秒精度 |

### 1.3 通用字段

| 字段 | 类型 | 说明 | 适用 |
| --- | --- | --- | --- |
| created\_at | DATETIME NOT NULL DEFAULT CURRENT\_TIMESTAMP | 创建时间 | 所有表 |
| updated\_at | DATETIME NOT NULL DEFAULT CURRENT\_TIMESTAMP ON UPDATE CURRENT\_TIMESTAMP | 更新时间 | 可变表 |
| deleted | TINYINT(1) NOT NULL DEFAULT 0 | 逻辑删除（0 正常，1 已删除） | 用户、群、文件、AI 会话 |

以下各表字段表中，凡标注「通用」的字段不再逐表重复说明含义。

### 1.4 逻辑删除与唯一键

- 用户与群采用逻辑删除。为避免已删除记录占用唯一键，删除时将 username 改写为 username#id，群号保持不变且不回收。
- 好友关系、群成员采用状态位或物理删除，不使用 deleted 字段（见各表说明），以保证联合唯一键可复用。
- 「同一对象只允许一条待处理申请」使用 pending\_flag 技巧：待处理时置 1，处理后置 NULL，配合联合唯一键，MySQL 唯一索引允许多个 NULL，从而保留历史记录。

### 1.5 ID 策略

- 自增 ID：用户、群、会话等低频写入表。
- 雪花 ID：t\_message，64 位（41 位时间戳 + 10 位节点 + 12 位序列），时间有序，便于对外暴露与日后分库。
- 群号（group\_no）：对外展示的 8 位数字，随机生成并唯一，不暴露自增 ID。
- 特殊用户：sender\_id = 0 表示系统，sender\_id = -1 表示 AI 机器人，不在 t\_user 中建行。

### 2.2 实体关系

```
t_user 1──n t_refresh_token / t_login_log / t_notice / t_file(uploader)
t_user n──n t_user          经 t_friend（双向两行）
t_user 1──n t_friend_request n──1 t_user
t_user n──n t_group         经 t_group_member
t_group 1──n t_group_request n──1 t_user
t_group 1──1 t_conversation（type=2，biz_key=G:groupId）
t_friend 1──1 t_conversation（type=1，biz_key=P:小ID_大ID）
t_conversation 1──n t_message 1──n t_message_mention
t_conversation 1──n t_user_conversation n──1 t_user
t_user 1──n t_ai_session 1──n t_ai_message
t_user 1──n t_ai_usage（按日）      t_ai_model 被 t_ai_session 引用（model_code）
```

### 3.11 t\_message 聊天消息表

本系统数据量最大的表。消息只增不改（撤回仅改 status），读取以 (conversation\_id, seq) 游标分页。

| 字段 | 类型 | 约束或默认 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK（雪花，非自增） | 消息 ID |
| conversation\_id | BIGINT | NOT NULL | 所属会话 |
| seq | BIGINT | NOT NULL | 会话内递增序号 |
| sender\_id | BIGINT | NOT NULL | 发送人；0 系统，-1 AI 机器人 |
| msg\_type | TINYINT | NOT NULL | 1 文本，2 图片，3 文件，4 系统消息，5 AI 回复 |
| content | TEXT | NULL | 文本内容；图片与文件存说明文字或空 |
| extra | JSON | NULL | 附件信息（fileId、url、name、size、width、height）、@用户、系统消息参数等 |
| reply\_to\_msg\_id | BIGINT | NULL | 引用回复的消息 ID |
| client\_msg\_id | VARCHAR(40) | NOT NULL | 客户端消息 ID（幂等） |
| status | TINYINT | NOT NULL 默认 0 | 0 正常，1 已撤回，2 管理员删除 |
| recalled\_at | DATETIME | NULL | 撤回时间 |
| recalled\_by | BIGINT | NULL | 撤回人（本人或管理员） |
| created\_at | DATETIME(3) | NOT NULL | 发送时间 |

索引：uk\_conv\_seq(conversation\_id, seq)；uk\_sender\_client(sender\_id, client\_msg\_id)；idx\_conv\_time(conversation\_id, created\_at)；idx\_sender(sender\_id, created\_at)；ft\_content(content) FULLTEXT WITH PARSER ngram。

extra 示例：

```json
{ "file": { "id": 1001, "url": "/files/2026/10/a.png", "name": "a.png", "size": 20480, "w": 800, "h": 600 },
  "mentions": [3, 8], "mentionAll": false }
```

撤回后接口层对 content 与 extra 脱敏，仅返回「消息已撤回」；数据库保留原文以便审计，保留期满后清空。

## 7 关键 SQL 与索引命中

| 场景 | SQL 要点 | 命中索引 |
| --- | --- | --- |
| 会话列表 | 联表 t\_user\_conversation 与 t\_conversation，WHERE user\_id=? AND hidden=0 ORDER BY pinned DESC, last\_active\_at DESC | idx\_user\_sort |
| 最新消息 | WHERE conversation\_id=? AND seq>GREATEST(?, ?) ORDER BY seq DESC LIMIT 30（两个参数为成员 joined\_seq 与 clear\_seq） | uk\_conv\_seq |
| 向上翻页 | WHERE conversation\_id=? AND seq&#60;? AND seq>? ORDER BY seq DESC LIMIT 30 | uk\_conv\_seq |
| 断线补拉 | WHERE conversation\_id=? AND seq>? ORDER BY seq ASC LIMIT 200 | uk\_conv\_seq |
| 关键字搜索 | WHERE conversation\_id=? AND MATCH(content) AGAINST(? IN BOOLEAN MODE) AND status=0，可叠加 created\_at、sender\_id、msg\_type 过滤 | ft\_content，再按会话过滤 |
| 定位上下文 | 取 seq 前后各 20 条：seq BETWEEN ?-20 AND ?+20 | uk\_conv\_seq |
| 好友列表 | WHERE user\_id=? | uk\_pair（前缀） |
| 群成员 | WHERE group\_id=? AND status=0 ORDER BY role DESC, joined\_at | idx\_group\_role |
| 我的群 | WHERE user\_id=? AND status=0 | idx\_user\_status |
| 待审批申请 | WHERE group\_id=? AND status=0 | idx\_group\_status |
| @我的消息 | WHERE user\_id IN (?, 0) AND conversation\_id=? AND seq>? | idx\_user\_conv\_seq |
| 未读红点 | WHERE user\_id=? AND is\_read=0 | idx\_user\_read |
| 登录限流统计 | WHERE ip=? AND created\_at>? | idx\_ip\_time |

未读数更新（群消息，在发送事务内或紧随其后异步执行）：

```sql
UPDATE t_user_conversation uc
JOIN t_group_member gm ON gm.user_id = uc.user_id AND gm.group_id = ? AND gm.status = 0
SET uc.unread_count = uc.unread_count + 1, uc.hidden = 0, uc.last_active_at = ?
WHERE uc.conversation_id = ? AND uc.user_id <> ?;
```

消息可见范围：用户仅可见 seq 大于 GREATEST(joined\_seq, clear\_seq)，且（left\_seq 为 NULL 或 seq 小于等于 left\_seq）的消息；私聊无 joined\_seq，仅应用 clear\_seq。

## 8 事务与一致性

| 业务操作 | 事务内包含的写入 | 注意事项 |
| --- | --- | --- |
| 同意好友申请 | 更新 t\_friend\_request；插入两行 t\_friend；创建或获取私聊 t\_conversation；插入双方 t\_user\_conversation；写 t\_notice | 申请行使用 SELECT ... FOR UPDATE 防并发重复处理 |
| 创建群 | 插入 t\_group；创建群 t\_conversation 并回填 conversation\_id；插入群主 t\_group\_member 与 t\_user\_conversation；邀请成员批量插入 | 群号冲突时重试生成 |
| 加入群 | 更新申请；插入或复用 t\_group\_member（记录 joined\_seq）；插入 t\_user\_conversation；member\_count 加 1；写系统消息 | 先校验人数上限，使用 UPDATE ... WHERE member\_count < max\_members 原子加一 |
| 退群或踢人 | 更新 t\_group\_member（status、left\_seq、left\_at）；member\_count 减 1；写系统消息；清缓存 | 群主不可直接退群，须先转让 |
| 转让群主 | 更新 t\_group.owner\_id；原群主 role 改为管理员，新群主 role 改为 2 | 一个事务内完成，防止出现双群主 |
| 发送消息 | 插入 t\_message；更新 t\_conversation.last\_\*；更新相关 t\_user\_conversation；插入 t\_message\_mention | 主链路只保证 t\_message 落库，其余可异步，失败可由 seq 对账修复 |
| 撤回消息 | 更新 t\_message.status、recalled\_at、recalled\_by；必要时更新会话 last\_preview | 校验发送人与 120 秒时限 |
| 注销用户 | 更新 t\_user（deleted、username 改写）；撤销令牌；退出所有群；处理其拥有的群（先转让或解散） | 保留历史消息，昵称显示为已注销用户 |

死锁规避：涉及多行的更新按主键升序加锁；涉及双方用户的操作（如好友关系）固定以较小 ID 优先。

## 9 容量估算与数据生命周期

### 9.1 容量估算

假设 1000 日活，人均每日 100 条消息：每日约 10 万条，每年约 3650 万条；单条消息含索引平均按 600 字节估算，年增约 22 GB。一般 SSD 的单机 MySQL 可支撑 2–3 年；超过 1 亿行或单表超过 100 GB 时启动归档或分库分表。

### 9.2 清理与归档策略

| 数据 | 保留策略 | 实现 |
| --- | --- | --- |
| t\_login\_log | 90 天 | 每日凌晨定时删除 |
| t\_refresh\_token | 过期或撤销满 7 天删除 | 定时任务 |
| t\_friend\_request、t\_group\_request | 超时未处理置为已过期；终态记录保留 1 年 | 每小时任务置过期，每日清理 |
| t\_notice | 已读满 90 天删除 | 定时任务 |
| t\_file | 状态为待清理且满 7 天，同时删除物理文件 | 每日任务（先校验无消息引用） |
| t\_operation\_log | 1 年，满后导出归档 | 定时任务 |
| t\_message | 永久保留；撤回消息原文 30 天后清空 content 与 extra | 定时任务；超量时按月归档到历史表 |
| t\_ai\_message | 随会话保留；用户删除会话后物理清理 | 逻辑删除 30 天后物理删除 |

### 9.3 扩展路线

1. 读写压力增大：增加 MySQL 只读副本，历史查询与后台统计走只读库。
2. 消息表过大：按 conversation\_id 哈希分表（如 16 张），或按月分区（注意分区表限制：全文索引不可用，需改用 Elasticsearch 搜索）。
3. 搜索：消息写入后经异步通道同步到 Elasticsearch，MySQL 全文索引作为小规模方案。

## 10 数据库变更管理

- 使用 Flyway 管理脚本，目录 db/migration，命名 V{版本}\_\_{说明}.sql，禁止修改已发布脚本，变更以新增脚本进行。
- 变更遵循先加后删：新增字段先允许 NULL 或带默认值，发布应用后再收紧约束；删除字段需经过一个发布周期的只读观察。
- 生产环境大表加索引使用 ALGORITHM=INPLACE, LOCK=NONE，并在低峰期执行。
- 每日全量备份加 binlog 增量，保留 7 天；每月做一次恢复演练。
